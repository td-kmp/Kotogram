## 1. The contract sheet

Format: **Rule** — exact quote — source. Every rule here is [V] unless marked.

### 1.1 Transport, threads and order

- **One receiver, any thread, in order.** "New updates and responses to requests can be received through td_receive from any thread after the first request has been sent to the client instance. This function must not be called simultaneously from two different threads. Also, note that all updates and responses to requests must be applied in the order they were received for consistency." — `td/telegram/td_json_client.h:26-29`. Same in `td/telegram/Client.h:24-27` ("should be applied in the same order as they were received, to ensure consistency").
- **Dedicated thread advised.** "Given this information, it's advisable to call this function from a dedicated thread." — `td/telegram/Client.h:182`.
- **Order is a TDLib guarantee.** "TDLib guarantees that all updates are delivered in the right order." — core.telegram.org/tdlib/docs (Features). "All updates and responses to requests must be handled in the order they are received." — getting-started, "Handling updates".
- **No updates before the first request.** "The TDLib instance will not send updates until the first request is sent to it." — `td_json_client.h:52-53`. Consequence for the given library: `TdClient.updates` has replay 0 (`TdClient.kt:34`), so **the collector of `updates` must be attached before the first `send`**; `authorizationState` is the only state that is "never missed" (`TdClient.kt:25-26`). See §8 for what this means for `DefaultClientHolder`.
- **`@extra` and `@client_id`.** "To match requests with a corresponding response, the field "@extra" can be added to the request object... Each returned object will have an "@client_id" field" — `td_json_client.h:19-22`. The library already does this (`TdReceiver.kt:47-50, 76-84`).
- **Synchronous execute.** "A request can be executed synchronously, only if it is documented with "Can be called synchronously"." — `td_json_client.h:74`. `getPushReceiverId` and `setLogVerbosityLevel`, `getOption` for some options, `getTextEntities` qualify (`td_api.tl:16015`, options page: `version` "can be received synchronously").
- **Close before exit.** "All TDLib client instances must be closed before application termination to ensure data consistency." — `td_json_client.h:31`. Kotogram does this on `stopKoin()` (`core/tdlib/.../DefaultClientHolder.kt:89-95`).

### 1.2 What the app must cache, what it may fetch

- **Five caches are mandatory, keyed by id, fed by update.** For chats/users/basic groups/supergroups/secret chats the getting-started page says, per entity: "Instead it must maintain a cache of users received through this update" and "whenever an Application receives a user_id, it never needs to use the getUser request to receive the user object" (same sentence pattern for `chat_id`/`getChat`, `basic_group_id`/`getBasicGroup`, `supergroup_id`/`getSupergroup`, `secret_chat_id`/`getSecretChat`) — getting-started, "Handling updates".
- **Ordering guarantee behind that.** "This update is guaranteed to come before the chat identifier is returned to the application. The chat field changes will be reported through separate updates" — `updateNewChat`, `td_api.tl:10844`. Identical wording for `updateUser` (:11094), `updateBasicGroup` (:11097), `updateSupergroup` (:11100), `updateSecretChat` (:11103), and also for saved-messages topics (:10977), direct-messages topics (:10984), quick-reply shortcuts (:10994) and communities (:11088).
- **Consequence: a message's `sender_id`, `chat_id`, a chat's `type.user_id` can be resolved from the caches with a plain map lookup.** Paper Plane relies on it so hard it panics on a miss ("TDLib guarantees that types are always returned before their ids" — `src/model/client_state_session.rs:147-153, 174-179`). Unigram uses `TryGet*` everywhere and tolerates a miss (`Telegram/Services/ClientService.cs:2329-2334, 2488`).
- **Full infos are not guaranteed; fetch them.** `updateUserFullInfo` / `updateSupergroupFullInfo` / `updateBasicGroupFullInfo` say only "Some data in userFullInfo has been changed" (`td_api.tl:11106-11113`); Unigram calls `GetUserFullInfo` etc. lazily (`ClientService.cs:1727 LoadFullInfo`).
- **Messages are not a cache TDLib keeps for you in memory.** `getMessage` "Returns a 404 error if the message doesn't exist" (`:11900`); `getMessageLocally` "if it is available without sending network request... This is an offline method" (`:11905`). Option `message_unload_delay`: "Maximum seconds messages stay in memory before unloading (60-86400); defaults to 60 for users" — options page [V, paraphrase by the fetcher].
- **Files: track `updateFile`.** "The handling of this update is essential to follow the progress of files being downloaded or uploaded." — getting-started. `getFile` "This is an offline method" (`:11962`).
- **Chat `client_data`.** "Application-specific data associated with the chat... Persistent if the message database is used" — `td_api.tl:3936`. An official place for per-chat app state (scroll position etc.).

### 1.3 Chat lists

- **Order is `(position.order, chat.id)` descending.** "Chats must be sorted by the pair (order, chat.id) in descending order" — `chatPosition.order`, `td_api.tl:3851`. Repeated at `loadChats` (:11971).
- **Three position-carrying updates.** `updateChatPosition` "The position of a chat in a chat list has changed. An updateChatLastMessage or updateChatDraftMessage update might be sent instead of the update... If new order is 0, then the chat needs to be removed from the list" (`:10871-10874`); `updateChatLastMessage ... positions:vector<chatPosition>` "The new chat positions in the chat lists" (`:10865-10869`); `updateChatDraftMessage ... positions` (`:10897-10901`). `chat.positions` on `updateNewChat` is the initial set (`:3904`).
- **Membership vs position are different things.** "A chat can have a non-zero position in a chat list even if it doesn't belong to the chat list and have no position in a chat list even if it belongs to the chat list" — `chat.chat_lists`, `td_api.tl:3905`; `updateChatAddedToList` / `updateChatRemovedFromList` (`:10876-10880`). Unigram keeps `Chat.ChatLists` separately from positions (`ClientService.cs:3696-3755`) and ignores it for ordering.
- **`is_pinned` and `source` are display attributes; they are already folded into `order`.** `chatPosition is_pinned:Bool source:ChatSource` "True, if the chat is pinned... Source of the chat in the chat list; may be null" (`:3852-3853`); sources are `chatSourceMtprotoProxy` and `chatSourcePublicServiceAnnouncement` (`:3842-3846`). Neither client sorts by `is_pinned` [V: Unigram `ChatListViewModel.cs:660-668` compares order then id; Paper Plane `src/model/chat_list.rs:197-198` keys a `BTreeMap` by `-order`].
- **`loadChats` is the paging call; the data arrives as updates; 404 is the end.** "Loads more chats from a chat list. The loaded chats and their positions in the chat list will be sent through updates... Returns a 404 error if all chats have been loaded"; "the number of loaded chats is chosen by TDLib and can be smaller than the specified limit, even if the end of the list is not reached" — `td_api.tl:11971-11974`. `getChats` is "For informational purposes only. Use loadChats and updates processing instead" (`:11976`). Both clients loop `loadChats` until 404 (Unigram `Services/OrderedSourceService.cs:202-235`, Paper Plane `src/model/chat_list.rs:144-158`).
- **Archive auto-moves.** "Unmuted chats are automatically moved from the Archive to the Main chat list when a new message arrives" — `chatListArchive`, `:3830`.
- **Folders.** `updateChatFolders chat_folders main_chat_list_position are_tags_enabled` (`:10965-10969`); a folder list is `chatListFolder chat_folder_id` (`:3834`).
- **Counters need the message database.** `updateUnreadMessageCount` / `updateUnreadChatCount` "This update is sent only if the message database is used" (`:11236, :11242`); `total_count` is "Approximate total number of chats in the chat list" (`:11244`).

### 1.4 Chat history

- **`getChatHistory` returns fewer than asked, newest first.** "The messages are returned in reverse chronological order (i.e., in order of decreasing message_id). For optimal performance, the number of returned messages is chosen by TDLib. This is an offline method if only_local is true"; `from_message_id` "use 0 to get results from the last message"; `offset` "Specify 0 to get results from exactly the message from_message_id or a negative number from -99 to -1 to get additionally -offset newer messages"; `limit` "must be positive and can't be greater than 100. If the offset is negative, then the limit must be greater than or equal to -offset"; `only_local` "Pass true to get only messages that are available without sending network requests" — `td_api.tl:12213-12221`. Same shape for `getMessageThreadHistory` (`:12223-12231`).
- **Practical consequence [V in both clients]:** page until an empty result; a short page is not the end (Unigram treats `MessagesValue.Empty()` as `endReached`, `ViewModels/DialogViewModel.cs:1023`; Paper Plane returns `Ok(false)` only on empty, `src/model/chat_history_model.rs:128-130`). Unigram also re-asks with `only_local=false` when a local page has fewer than 5 messages or is out of range (`DialogViewModel.cs:1657-1688`).
- **Jump by date.** `getChatMessageByDate` "Returns the last message sent in a chat no later than the specified date. Returns a 404 error if such message doesn't exist" (`:12353-12356`).
- **Replies.** `getRepliedMessage` "Returns information about a non-bundled message that is replied by a given message... Returns a 404 error if the message doesn't exist" (`:11910-11921`).
- **Albums.** `message.media_album_id` "Unique identifier of an album this message belongs to; 0 if none. Only audios, documents, photos and videos can be grouped together in albums" (`:3466`). Grouping is the app's job (Unigram `DialogViewModel.cs:2218-2300 ProcessAlbums`).

### 1.5 openChat / closeChat / viewMessages

- **Open is mandatory for channel/supergroup updates.** "Informs TDLib that the chat is opened by the user. Many useful activities depend on the chat being opened or closed (e.g., in supergroups and channels all updates are received only for opened chats)" — `openChat`, `td_api.tl:13612`; `closeChat` (`:13615`).
- **View is what marks read and keeps counters.** "Informs TDLib that messages are being viewed by the user... Many useful activities depend on whether the messages are currently being viewed or not (e.g., marking messages as read, incrementing a view counter, updating a view counter, removing deleted messages in supergroups and channels)"; `source` "pass null to guess the source based on chat open state"; `force_read` "Pass true to mark as read the specified messages even if the chat is closed" — `:13618-13624`. Sources: `messageSourceChatHistory`, `messageSourceChatList`, `messageSourceOther`... (`:3516-3547`).
- **Online member count only for opened chats.** `updateChatOnlineMemberCount` "sent only for currently opened chats" (`:10971`).
- **Who does it in the clients.** Unigram: `OpenChat` on navigate-to (`DialogViewModel.cs:2670`), `CloseChat` on navigate-from (`:2896`), `ViewMessages(... MessageSourceChatHistory, force_read:true)` from the view (`:4603`, `Services/ClientService.cs:480`). Paper Plane: `open_chat`/`close_chat` when the history widget's chat changes (`src/ui/session/content/chat_history.rs:341, 421`) and `view_messages` after the first load (`:406`).

### 1.6 updateNewMessage vs updateChatLastMessage

- **They are different streams.** `updateNewMessage` "A new message was received; can also be an outgoing message" (`:10762`). `updateChatLastMessage.last_message` "may be null if the last message became unknown. While the last message is unknown, new messages can be added to the chat without corresponding updateNewMessage update" (`:10867`).
- **Consequence [V]:** a chat list row is driven by `updateChatLastMessage` (plus `updateNewChat.chat.last_message`), never by `updateNewMessage`; an open history is driven by `updateNewMessage`, and on `last_message == null` must consider its newest slice stale. Unigram does exactly that: `Handle(UpdateChatLastMessage)` with `LastMessage == null` sets `IsNewestSliceLoaded = null` (`ViewModels/DialogViewModel.Handle.cs:655-660`).
- **History loaded by `getChatHistory` produces no `updateNewMessage`** [I from the two doc lines above and both clients' code; not stated in one sentence].

### 1.7 Sending: state and id replacement

- **Temporary id, then a different one.** `messageSendingStatePending sending_id` (`:3343-3344`); `updateMessageSendSucceeded message old_message_id` "The sent message. Almost any field of the new message can be different from the corresponding field of the original message... @old_message_id The previous temporary message identifier" (`:10771-10775`); `updateMessageSendFailed ... error` "Be aware that some messages being sent can be irrecoverably deleted, in which case updateDeleteMessages will be received instead of this update" (`:10777-10781`); `messageSendingStateFailed can_retry retry_after ...` "No update is sent when this field changes" (`:3346-3354`).
- **Quick ack is opt-in.** `updateMessageSendAcknowledged` "sent only if the option "use_quick_ack" is set to true. This update may be sent multiple times for the same message" (`:10765-10769`).
- **Deletion flags.** `updateDeleteMessages is_permanent from_cache` "from_cache True, if the messages are deleted only from the cache and can possibly be retrieved again in the future" (`:11058-11063`). Both clients ignore `from_cache == true` for the UI (Unigram `DialogViewModel.Handle.cs:906`, Paper Plane `src/model/chat.rs:241-243`).

### 1.8 Files

- **Shape.** `file id size expected_size local remote` (`:305-311`); `localFile path can_be_downloaded can_be_deleted is_downloading_active is_downloading_completed download_offset downloaded_prefix_size downloaded_size` (`:283-292`); `remoteFile id unique_id is_uploading_active is_uploading_completed uploaded_size` (`:294-303`).
- **Id lifetime.** `file.id` is "Unique file identifier" (`:306`) with no persistence claim; `remote.id` "Can be used by the current user across application restarts or even from other devices. Uniquely identifies a file, but a file can have a lot of different valid identifiers"; `remote.unique_id` "the same for the same file even for different users and is persistent over time" (`:295-299`). Rule: **`file.id` is a session handle; persist `remote.id`/`unique_id`**. Unigram keys its download-folder state by `Remote.UniqueId` (`Services/ClientService.Files.cs:245-260, 298-305`) and puts the session id into the in-memory routing token because "a file id only identifies a file within one [session]" (`Common/UpdateManager.cs:57-66`).
- **downloadFile.** "Download progress and completion of the download will be notified through updateFile updates"; `priority` "(1-32). The higher the priority, the earlier the file will be downloaded. If the priorities of two files are equal, then the last one for which downloadFile/addFileToDownloads was called will be downloaded first"; `limit` "use 0 to download without a limit"; `synchronous` "Pass true to return response only after the file download has succeeded, has failed, has been canceled, or a new downloadFile request with different offset/limit parameters was sent; pass false to return file state immediately" — `:14373-14379`. `cancelDownloadFile only_if_pending` (`:14384`). `addFileToDownloads` "If message database is used, the list of file downloads is persistent across application restarts. The downloading is independent of download using downloadFile" (`:14427-14433`). `updateFile` "Information about a file was updated" (`:11129`); no completion-specific update exists, completion is `local.is_downloading_completed`.
- **Priorities in practice [V]:** Unigram uses 16 for an explicit open, 30 for downloads-manager, 1 for streaming reads with offset/limit (`ClientService.Files.cs:206, 292, 547`); Paper Plane uses 5 everywhere (`src/model/client_state_session.rs:284, 320`).
- **Storage.** `optimizeStorage` (`:16381-16391`), `deleteFile` (`:14424`), option `use_storage_optimizer` ("the background storage optimizer will be enabled"), `storage_max_time_from_last_access` set by Unigram (`ClientService.cs:546`) [U: not on the current options page as fetched; it exists in TDLib's `OptionManager` and is accepted at runtime by Unigram's build].
- **Non-file-path environments (web).** "readFilePart... This method is intended to be used only if the application has no direct access to TDLib's file system, because it is usually slower than a direct read from the file" (`:14418-14422`); `updateFileGenerationStart` "If the application has no access to the path, it can use writeGeneratedFilePart" (`:11136`). In tdlib-kmp's web target TDLib runs in a Web Worker that "also owns storage: what is mounted where, and when it is written, is the application's. Paths in `setTdlibParameters` are paths in the worker's file system" (`core/webMain/io/xbot/tdlib/WorkerTdLib.kt:20-22`). **Design consequence:** the image layer must take a `File` and produce bytes/URI through one platform seam (`local.path` on JVM/Android/iOS, `readFilePart` or a worker-side blob on web), never read `local.path` directly in common code. Paper Plane and Unigram both read `local.path` directly (desktop-only).

### 1.9 Notifications

- **Opt in with an option.** "To enable the TDLib Notificaition API you need to set option `notification_group_count_max` to a positive value" (0-25, default 0); `notification_group_size_max` 1-25, default 10 — notification-api page. Both clients set it: Unigram 25 (`ClientService.cs:545`), Paper Plane 5 (`src/model/client.rs:120-125`, again in `client_state_session.rs:78-83`).
- **Four group types.** `notificationGroupTypeMessages | Mentions | SecretChat | Calls` (`td_api.tl:9184-9193`); `notificationGroup id type chat_id total_count notifications` where id is "Unique persistent auto-incremented from 1 identifier" (`:9216-9222`); `notification id date is_silent type` (`:9209-9214`).
- **Startup snapshot then deltas.** `updateActiveNotifications` "Contains active notifications that were shown on previous application launches. This update is sent only if the message database is used. In that case it comes once before any updateNotification and updateNotificationGroup update" (`:11050-11051`). `updateNotificationGroup ... notification_settings_chat_id notification_sound_id total_count added_notifications removed_notification_ids` ("total_count... can be bigger than number of active notifications") (`:11039-11048`); "Whenever possible, `updateNotificationGroup` updates for a group are combined into a single update" and clients should apply them immediately because TDLib already manages delays — notification-api page. `updateNotification` "A notification was changed" (`:11036`), including type change `NewPushMessage` → `NewMessage` (notification-api page).
- **Keep-alive signal.** `updateHavePendingNotifications have_delayed_notifications have_unreceived_notifications` "Can be used to prevent application from killing, while there are some pending notifications" (`:11053-11056`).
- **Push.** `registerDevice device_token other_user_ids` "Returns a globally unique identifier of the push notification subscription... @other_user_ids List of user identifiers of other users currently using the application" (`:16008-16009`); `processPushNotification payload` "Returns error with code 406 if the push notification is not supported and connection to the server is required to fetch new data. Can be called before authorization"; payload is "JSON-encoded push notification payload with all fields sent by the server, and "google.sent_time" and "google.notification.sound" fields added" (`:16011-16013`); `getPushReceiverId payload` "Returns a globally unique push notification subscription identifier for identification of an account, which has received a push notification. Can be called synchronously" (`:16015-16016`); if it returns 0 "all clients should process the push" (notification-api page). `notificationTypeNewPushMessage` "The message will not be available in the chat history, but the identifier can be used in viewMessages, or as a message to be replied" (`:9172-9178`).
- **Settings updates.** `updateChatNotificationSettings`, `updateScopeNotificationSettings` (`:10914, :11030`).

### 1.10 Options to set, network, online

- **Writable options that matter here (options page [V]):** `online` ("Online status of the current user"), `notification_group_count_max`, `notification_group_size_max`, `use_quick_ack`, `message_unload_delay`, `use_storage_optimizer`, `ignore_background_updates` ("no effect if a database or secret chats are used"), `localization_target`, `language_pack_id`, `language_pack_database_path`, `prefer_ipv6`, `use_pfs`, `disable_persistent_network_statistics`, `disable_contact_registered_notifications` ("Call getOption to fetch the latest value"), `ignore_sensitive_content_restrictions` (same), `utc_time_offset` ("Reset on each launch"), `always_parse_markdown`, `disable_top_chats`, `ignore_file_names`. - **Read-only options worth caching from `updateOption`:** `my_id`, `version` ("Guaranteed to arrive before all other updates"), `unix_time`, `is_premium`, `is_premium_available`, `authorization_date`, `test_mode`, `t_me_url`, `pinned_chat_count_max`, `message_text_length_max`, `message_caption_length_max`, `forwarded_message_count_max` and the other limits (options page). - **setNetworkType.** "Calling this method forces all network connections to reopen, mitigating the delay in switching between different networks, so it must be called whenever the network is changed, even if the network type remains the same. Network type is used to check whether the library can use the network at all and also for collecting detailed network data usage statistics" — `td_api.tl:16394-16397`. `connectionStateWaitingForNetwork` "Use setNetworkType to change the available network type" (`:10285`). Unigram sends it on every OS connectivity change and never sends `networkTypeNone` (it maps "no profile" to WiFi, `Services/NetworkService.cs:56-102`).
- **`online`.** Unigram sets it from window activation (`App.xaml.cs:97-98`), to `false` when a session stops being the active one (`Services/Session.cs:133-136`) and to `false` at startup (`ClientService.cs:543`). Paper Plane exposes `set_online` (`src/model/client.rs:205-222`). `updateConnectionState` "must be used only to show a human-readable description of the connection state" (`:11339`).

### 1.11 Authorization, closing, restart

- **Sequence.** "The first authorization state received by the Application is always of the type authorizationStateWaitTdlibParameters... If setTdlibParameters fails, then authorization state is not changed" — getting-started. `setTdlibParameters` "Works only when the current authorization state is authorizationStateWaitTdlibParameters" (`td_api.tl:11669`); `use_message_database` "Implies use_chat_info_database", which "Implies use_file_database" (`:11674-11676`).
- **Three ways out.** `close` "All databases will be flushed to disk and properly closed. After the close completes, updateAuthorizationState with authorizationStateClosed will be sent. Can be called before initialization" (`:11784`); `logOut` "Requires an available network connection. All local data will be destroyed" (`:11781`); `destroy` "destroying all local data without a proper logout. The current user session will remain in the list of all active sessions" (`:11787-11789`).
- **Closing semantics.** `authorizationStateClosing` "all subsequent queries will be answered with the error 500. Note that closing TDLib can take a while" (`:246`); `authorizationStateClosed` "No other updates will be received after this. All queries will be responded to with error code 500. To continue working, one must create a new instance of the TDLib client" (`:249-251`).
- **Both clients reset every cache on `Closed` and (optionally) start a new instance in the same slot:** Unigram `Clear()` then `Initialize()` (`ClientService.cs:3763-3764, 869-1041`), Paper Plane removes the client (`src/model/client_manager.rs:255-260`). Kotogram's `DefaultClientHolder` already loops on `Closed` (`core/tdlib/.../DefaultClientHolder.kt:66-71`).

## 2. Push notifications for a third-party app

### Verified
- **Server-side credentials are mandatory and live in the app's settings on my.telegram.org.** "To use specific push notification service, the correct application platform must be specified and a valid server authentication data must be uploaded at https://my.telegram.org" — `td_api.tl:8721-8722` (`@class DeviceToken`). The MTProto page says "application certificates (APNS) or an application key (GCM) must be specified in the application settings" and links to `/myapp` — core.telegram.org/api/push-updates [V]. Token types: `deviceTokenFirebaseCloudMessaging token encrypt` (`:8724-8725`), `deviceTokenApplePush device_token is_app_sandbox` (`:8727-8728`), `deviceTokenApplePushVoIP ... encrypt` (`:8731`), plus WNS, web push, Huawei, etc. (push-updates page).
- **Payload.** FCM data message with a `p` field: "base64url-encoded encrypted MTProto payload", decrypted with the key passed to `registerDevice` (`secret` in MTProto, `encrypt=true` in TDLib); fields `loc_key`, `custom`, and `user_id` "ID of the account to which the PUSH notification should be delivered... in case of clients with multiple accounts active and running" — push-updates page [V].
- **TDLib side.** `registerDevice` once per authorized account, passing the other accounts' user ids; `getPushReceiverId(payload)` (synchronous, before any instance exists) to pick the account; `processPushNotification(payload)` on that account's instance; 406 means "connection to the server is required to fetch new data" (`td_api.tl:16008-16016`); `updateHavePendingNotifications` tells when it is safe to stop (`:11053-11056`).
- **What Telegram X does (Android, multi-account) [V]:** FCM `onNewToken` → `TdlibManager.setDeviceToken` for every account (`service/PushHandler.kt:14-20`); `onMessageReceived` → `PushProcessor.processPush` (`PushHandler.kt:22-30`). `PushProcessor` runs `Client.execute(GetPushReceiverId(payload))`, maps the receiver id to a stored account, falls back to "all accounts" (`service/PushProcessor.java:64-74`), takes a wake lock and, if the job runs long or the device is dozing, promotes to a foreground service (`:147-283`). Per account `Tdlib.processPushOrSync` sends `ProcessPushNotification`, then waits for `updateActiveNotifications` and for the notification reference count to drop; on 401 it waits for `LoggingOut`/close; on any other error it performs a full `sync` (`telegram/Tdlib.java:6660-6707`). Registration: `RegisterDevice(token, otherUserIds)` with `otherUserIds` = the other accounts' user ids of the same DC mode, stored per account with the receiver id, retried via `SetAlarm` (`Tdlib.java:663-713`, `TdlibManager.java:1755-1790`); the token is `DeviceTokenFirebaseCloudMessaging(token, encrypt=true)` (`unsorted/Settings.java:6617`).
- **What Unigram does:** nothing. There is no `RegisterDevice` call in the app (grep over `Telegram/` finds only the generated API type); notifications are produced locally from `updateNotificationGroup` while the process runs (`Services/NotificationsService.cs:100-112, 484-532`), and it suppresses them while `ConnectionStateUpdating` because "it has been probably pushed already by WNS" (`:512-518`) — a leftover from the UWP WNS era [I].
- **What official Telegram-iOS does:** its Notification Service Extension decrypts the `p` payload itself with a stored key (`existingMasterNotificationsKey`, `decryptedNotificationPayload`), routes by key id across accounts, and fetches media over the network with a 25 s deadline; it does not use TDLib — `Telegram/NotificationService/Sources/NotificationService.swift` (GitHub raw, fetched) [V].

### Unverified / open
- **Whether my.telegram.org currently exposes a place to upload an FCM key or an APNs certificate for a third-party `api_id`.** The TL comment and the MTProto page say it must be done there, but neither page was inspected behind login in this session, and no 2024-2026 confirmation was found by search [U]. Treat as the first thing the developer checks by logging in. If the fields are not there, pushes for Kotogram are impossible until Telegram enables them, and the design must degrade to: foreground `updateNotificationGroup` (desktop, like Unigram) and OS-level background fetch.
- **iOS with TDLib.** An NSE cannot reasonably start a full TDLib instance per push (memory limit, 30 s), and no TDLib-based iOS client doing it was found in the clones. The realistic iOS designs are: (a) `encrypt=false`, show the server-rendered `loc_key`/`loc_args` text in the NSE and let the main app call `processPushNotification` on open; (b) `encrypt=true` and decrypt in the NSE with your own copy of the key as Telegram-iOS does — which requires reimplementing the payload decryption [I]. Neither verified against a TDLib client.
- **Android background.** TGX's foreground-service escalation exists because `processPushNotification` can need network (406) and Doze; a KMP app on Android needs the same shape (FCM service → `getPushReceiverId` → account scope → `processPushNotification` → wait for `updateHavePendingNotifications` false) [I].
- **Desktop (JVM).** No push service; the process is the push. Nothing to design beyond the foreground notification API.

**What the per-entity reactive graph costs [V/I]**
- Every TDLib object becomes a GObject with a hand-written property list; **fields not listed are dropped** (e.g. `Message` keeps 12 of the ~40 `message` fields, `src/model/message.rs:52-83`). Each schema change means editing the model, the setters and the `.blp` bindings.
- Objects are never evicted: `Chat.messages` grows for the life of the account (`src/model/chat.rs:82`, no removal besides `DeleteMessages` / `SendSucceeded`), `downloading_files` keeps dead senders (`client_state_session.rs:367-386`, the `retain` is commented out).
- Reference cycles are avoided with `WeakRef` upward (`Chat.session`, `Message.chat`, `ChatListItem.chat`) and strong downward; this is GLib's refcount discipline and has no Compose equivalent.
- `ChatList.update_chat_position` does a linear `find_chat_item_position` on every position update (`chat_list.rs:222-230`) — O(n) per update on the main thread.
- Everything, including JSON decoding, runs on the GTK main loop after one channel hop; there is no batching or coalescing, each update is applied and notifies immediately.
- Updates that arrive before `Ready` are queued and replayed into the session (`client.rs:271-274`): this is the design's answer to "the caches exist only after login", and it is correct only because TDLib sends chat/user updates after `Ready` anyway [I].

## 4. Three flows in Unigram, with line references

### 4.1 Cold start to chat list
1. `App()` → `LifetimeService.Initialize()` (`App.xaml.cs:70-81`) scans `LocalState/<id>` folders; authorized ones become `SessionImpl`s, the active id comes from `AppSettings.ActiveSession` (`Services/LifetimeService.cs:105-164`).
2. `SessionImpl` builds `ClientService` which runs `Initialize()`: `new Client(this)` (sends `GetOption("version")`, `Td/Client.cs:109-118`), then on a pool thread `SetOption` × 8 (`ignore_background_updates`, `language_pack_database_path`, `localization_target`, `language_pack_id`, `online=false`, `use_pfs`, `notification_group_count_max=25`, `storage_max_time_from_last_access`) and `SetTdlibParameters(...)` **without waiting for `WaitTdlibParameters`**, then `GetApplicationConfig` (`Services/ClientService.cs:515-563`).
3. The static `TdReceive` thread is already running (`ClientService.cs:453-463`). Updates flow into `OnResult`: `updateOption` → `OptionsService` (`:4261-4280`), `updateNewChat` → `_chats[...]`, `SetChatPositions` (`:3673-3689`), `updateUser` → `_users` (`:3645-3668`).
4. `updateAuthorizationState(Ready)` → `InitializeReady()`: `CreatePrivateChat(my_id)` and `LoadChats(main, 20)` (`:3766-3767, 591-598`). `_authorizationStateTask` completes so UI code awaiting `GetAuthorizationStateAsync` continues (`:1478-1487, 3771-3775`).
5. `MainViewModel` is created with the first folder or main list (`ViewModels/MainViewModel.cs:52-58`); `ChatListViewModel` creates `ItemsCollection`, which calls `LoadMoreItemsAsync(0)` immediately (`ChatListViewModel.cs:33-41, 517-528`).
6. `OnLoadMoreItemsAsync` → `ChatListService.GetChatsAsync(Count, 20)` → `OrderedSourceService.GetItemsAsyncImpl`: if the set is short and not full, `LoadChats(missing)`, then re-reads the set (`OrderedSourceService.cs:160-221`). Returned ids are resolved through `_clientService.GetChats(ids)`, placed with the order **the service holds now** (`ChatListViewModel.cs:555-592`), `UpdateWindow` then `Subscribe()` to `Changed` (`:596-599`), and `HasMoreItems` is `TotalCount >= 0` (`-1` means the service holds the full list, `ChatListService.cs:53-57`).
7. From here every `updateChatPosition`/`LastMessage`/`Draft` reaches the row through `SetChatPositions → ChatListService.SetOrder → Changed → ItemsCollection.Enqueue → DispatcherDrain → Place()` (`ClientService.ChatList.cs:54-83`, `WindowedCollection.cs:75-78, 96-206`).

### 4.2 Opening a chat and paging
1. `DialogViewModel.OnNavigatedToAsync` decides the anchor: a `message_id` argument → `LoadMessageSliceAsync(null, id)`; a saved scroll position whose `ReadInboxMaxId` still matches the chat → load from `lastVisibleId` at the saved pixel; otherwise `LoadMessageSliceAsync(null, LastReadInboxMessageId, Top)`; a left chat → from `long.MaxValue` (`DialogViewModel.cs:2581-2662`). Then `ToggleChatIsMarkedAsUnread(false)` if needed and `OpenChat` (`:2665-2671`).
2. `LoadMessageSliceAsync` guards with `_loadingSlice`, resets both end flags to `null`, runs `LoadMessageSliceImpl` on a pool thread and shows a placeholder after 200 ms (`:1413-1435`). The impl issues `GetChatHistory(chat, fromMessageId, HistoryOffset=-12, HistoryLimit=24, onlyLocal = alignment==Top)` and falls back to a network request when the local page is short (<5) or out of range (`:1657-1690`, `Constants.cs:73-74`). It computes the unread marker: walks the page from oldest to newest, picks the first incoming message above `LastReadInboxMessageId`, inserts a synthetic `Message` with `MessageHeaderUnread` content, and realigns to it (`:1716-1771`).
3. Back on the UI thread: `_groupedMessages.Clear()`, `ProcessMessages` (albums, synthetic headers, dice state), `Items.ReplaceSlice(messages)`, `IsNewestSliceLoaded = endReached`, scroll to the anchor or bottom, push the previous id on `_repliesStack` when jumping, and if the page had a single item load backward at once (`:1437-1555`).
4. Scrolling calls `LoadNextSliceAsync(direction)`: anchor is `Items[0]` (backward, `offset 0`) or `Items.Last` (forward, `offset -HistoryLimit`); the opposite end is trimmed **before** the request so the two mutations are not in one layout pass (`:937-968, 856-880`); `GetChatHistory(anchor.ChatId, fromMessageId, offset, 24, false)` (`:1001`); an empty answer sets `IsOldestSliceLoaded`/`IsNewestSliceLoaded` (`:1023, 1066-1073`); the slice goes through `ProcessMessages` and `Items.PrependSlice/AppendSlice` (`:1049-1063`).
5. Jump to a reply: `LoadMessageSliceAsync(previousId, targetId)`; if the target is already in `Items` it only scrolls, otherwise a fresh slice replaces the window (`:1373-1409`), and back navigation pops `_repliesStack` (`:1219-1221`).
6. Leaving: `OnNavigatedFrom` sends `CloseChat`, stores `ReadInboxMaxId`, last visible id and pixel per chat/topic, or clears them when the last visible item is the chat's last message (`:2876-2935`).

### 4.3 A live message arriving in an open chat
1. `TdReceive` → `ClientService.OnResult(UpdateNewMessage)`: only forum-topic bookkeeping, then `_aggregator.Publish(update)` (`ClientService.cs:4551-4553, 4583`). (The chat row is **not** updated here; that happens on the following `updateChatLastMessage`, `:3630-3643`.)
2. `DialogViewModel.Handle(UpdateNewMessage)` (subscribed at `DialogViewModel.Handle.cs:54`): if `ChatId` matches and the scheduling state fits, `CreateMessage` on the TDLib thread, then `BeginOnUIThread`: match against pending "typing" drafts, else `InsertMessage(message)`, play a sound for incoming (`:782-843`).
3. `InsertMessage`: **only if `IsNewestSliceLoaded == true`** — `ProcessMessages` (album merge), `InsertMessageInOrder` → `MessageCollection.InsertInOrder`, `TrimHistoryAfterInsert`; if the view is scrolled back and the message is the user's own pending one, it reloads the newest slice around it; otherwise the message is dropped and will be fetched when the user returns to the bottom (`DialogViewModel.Handle.cs:1633-1665`).
4. `MessageCollection.InsertItem` finds the index with the unsent-aware comparator (`SortsBefore`), inserts or merges date/topic separators and updates `IsFirst/IsLast` grouping (`ViewModels/Dialogs/MessageCollection.cs:258-293, 556-652`).
5. When the message was the user's own, `updateMessageSendSucceeded` arrives: `Handle(chatId, oldMessageId, ...)` on the UI thread finds the `MessageViewModel` by old key, `message.Replace(update.Message)`, re-keys it in `Items`, removes a duplicate if the new id already landed ("race condition"), updates the bubble in place via `Delegate?.UpdateContainerWithMessageId` (`DialogViewModel.Handle.cs:1317-1358, 1497-1567`).
6. `updateChatLastMessage` for the same chat then moves the row in every chat list (`ClientService.cs:3630-3643` → §4.1 step 7) and, if `last_message` is null, tells the open dialog its newest slice is unknown (`DialogViewModel.Handle.cs:655-660`).

## 5. Hidden rules (quirks and races the clients work around)

1. **Position updates can arrive while a page is in flight.** Unigram places a paged chat with the order the service holds *now*, not the order on the `Chat`, and tolerates a chat already inserted by an update (`ChatListViewModel.cs:560-586`); the service keeps `_orders` "so that taking it out does not depend on reading the item back" because the item moves under you (`OrderedSourceService.cs:43-44, 29-32`).
2. **A chat with a pending delete must not reappear from a position update** (`ClientService.ChatList.cs:59-67`).
3. **`updateChatLastMessage.last_message == null` means the open history may be missing messages** (TL `:10867`); Unigram invalidates `IsNewestSliceLoaded` (`DialogViewModel.Handle.cs:657-660`).
4. **A live message while scrolled up is dropped, not inserted** (`DialogViewModel.Handle.cs:1635-1659`): there is nothing to place it against (the same reasoning as the chat list window, `WindowedCollection.cs:19-21`).
5. **Unsent messages sort by date, not id.** "A message that has not been sent yet is given an identifier just above the newest one the chat knows, but the identifier the server hands back on success is unrelated to it, and in a private chat far above it" (`MessageCollection.cs:263-273`); pending dates are offset when one lands (`:295-300`).
6. **`updateMessageSendSucceeded` can arrive after the message already exists under its new id** (duplicate removed, `DialogViewModel.Handle.cs:1531-1537`).
7. **`updateDeleteMessages.from_cache == true` must not remove rows** (Unigram `DialogViewModel.Handle.cs:906`; Paper Plane `chat.rs:241-243`, pointing at a tdlibchat discussion about not notifying open/closed chats).
8. **`updateChatDraftMessage` may carry an old draft for the open chat** and "mustn't be applied" if the user changed it (TL `:10897`); Unigram checks the composer state first (`DialogViewModel.Handle.cs:595-600`).
9. **Files: no update when a file vanishes from disk.** "TDLib sends no update when a file disappears behind its back" — Unigram verifies existence once on first sight off-thread and otherwise relies on `FileNotFoundException` at use, then `DeleteFile` (`ClientService.cs:3235-3249`, `ClientService.Files.cs:209-222`). "TDLib reports a file as downloaded again every time it is asked for", so completion side effects must be idempotent (`ClientService.Files.cs:321-329`).
10. **Files arrive by the hundred in every history page**, nearly all already known: Unigram dedupes at parse time into one shared instance so every holder sees progress without lookups (`ClientService.cs:3206-3227`). `UpdateManager` then coalesces per file per UI hop (`UpdateManager.cs:366-390`).
11. **`loadChats` returns fewer than asked even when the list is not finished** (TL `:11973`), so "more" is decided by the 404, not by counts (`OrderedSourceService.cs:202-216`, `chat_list.rs:149-156`).
12. **`getChatHistory` with `only_local` can answer with a short or out-of-range page**; Unigram re-asks remotely (`DialogViewModel.cs:1657-1688`).
13. **Pushes vs updates double-notify.** Unigram suppresses toasts while `ConnectionStateUpdating` (`NotificationsService.cs:512-518`); TGX waits for `updateActiveNotifications` before declaring a push processed (`Tdlib.java:6683-6684`).
14. **Startup state is unknown until the first `updateAuthorizationState`**; Unigram parks UI on a `TaskCompletionSource` (`ClientService.cs:432, 1478-1487`); Paper Plane queues non-auth updates until `Ready` (`client.rs:292-299`).
15. **Two processes cannot share a TDLib database** (comment in `Common/AppPaths.cs:102`) — relevant for an Android NSE-like process or desktop multi-instance.
16. **`setNetworkType(None)` is avoided**: Unigram maps every unknown or local-only profile to WiFi rather than telling TDLib the network is gone (`NetworkService.cs:63-67, 79-84`) [I: to avoid TDLib stopping all traffic on a wrong detection].
17. **`Clear()` on `Closed` runs on the TDLib thread while the UI may be paging**; the list services are emptied, not replaced, because views hold them (`ClientService.cs:883-886`).

| Idea | Why it exists there | Why not here |
|---|---|---|
| `EventAggregator` typed pub/sub with weak subscribers and synchronous invoke on the TDLib thread | WinUI has no structured concurrency; VMs outlive pages; weak tables avoid leaks | `SharedFlow<Update>` + `filterIsInstance` collected in `viewModelScope`/Koin-scope coroutines gives typed fan-out with lifetime for free; `TdClient.updatesOf<T>()` already exists (`TdClient.kt:47`). |

| Paper Plane's one-OS-thread → unbounded channel → main loop hop | GTK is single-threaded | `TdClient.updates` already decouples the receive loop with an unbounded buffer (`TdClient.kt:33-34`); collect on `Dispatchers.Default`. |

## 8. Findings about the given library and the current Kotogram code (reported separately, as asked)

1. **`DefaultClientHolder.updates = instances.flatMapConcat { it.updates }` never advances past the first instance.** `TdClient.updates` is a `SharedFlow` that never completes (`TdClient.kt:34-35`; `TdReceiver` only removes the client from its map on `Closed`, `TdReceiver.kt:87-89`), and `flatMapConcat` waits for the inner flow to complete before subscribing to the next (kotlinx semantics). After the first `Closed` the holder's `updates` is silent forever, while `authorizationState` (built with `flatMapLatest`) keeps working. `core/tdlib/.../DefaultClientHolder.kt:58` [V in code; the `docs/design/sessions.md` §1 statement "updates ... completes on Closed" is out of date]. Fix options: `flatMapLatest` plus a synthetic boundary, or `transformLatest { client -> emitAll(client.updates.takeWhile { !(it is UpdateAuthorizationState && it.authorizationState is AuthorizationStateClosed) }); emit(closedMarker) }`.
2. **Replay 0 + eager start = lost updates for late collectors.** `start()` emits the client and sends `SetTdlibParameters` right away (`DefaultClientHolder.kt:79-86`); TDLib starts emitting on the first request (`td_json_client.h:52-53`). Any collector of `ClientHolder.updates` that attaches after that point misses `updateOption(version, my_id…)`, early `updateUser`/`updateNewChat` and, worst, `updateActiveNotifications` which "comes once" (TL `:11050`). The account cache collector must be created and collecting **before** `start()` sends anything — e.g. the holder exposes a hook or the cache is constructed in the same Koin scope and the holder's `init` waits for `updates.subscriptionCount >= 1`. This is the single most important ordering rule for the new architecture.
3. **Library web target changes file access** (§1.8): plan one platform seam for bytes-from-`File`; the library offers nothing for it beyond passing `readFilePart` through `send`.
4. **No batch receive in the library** (one `receive()`, one decode, one `tryEmit` per event, `TdReceiver.kt:60-66`); Unigram's and TGX's batching is a performance lever Kotogram does not have. Not blocking; noted for later.
